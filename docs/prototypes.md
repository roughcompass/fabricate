# Prototypes

Prototypes turns what a persona needs into several Salt prototypes, generated in parallel, checked by DE FabLab itself, and kept as versions. Feedback becomes lessons, which every later generation applies. See `openspec/changes/add-prototypes/` in the harness for the proposal, design, and specifications.

Everything Prototypes shows is generated by AI and uses fictional data. Don't enter client or confidential information: personas, intents, and code go to model providers through Vercel AI Gateway.

## Set up locally

Prototypes keeps its data in an in-process Postgres (PGlite) under `storage/prototypes-pglite`, apart from the SQLite database, so it needs no database account.

1. Install and migrate:

   ```sh
   npm ci
   npm run prototypes:migrate
   ```

   PGlite allows one process at a time, so stop `npm run dev` before migrating.

2. Give it a model credential, either an AI Gateway key or the project's OIDC token:

   ```sh
   export AI_GATEWAY_API_KEY=<key>
   # or, with the Vercel project linked:
   vercel env pull
   ```

   `vercel env pull` writes `VERCEL_OIDC_TOKEN` to `.env.local`. It expires after 12 hours; pull again when generation reports that it isn't configured. The same token also lets Open in Vercel Sandbox run locally.

3. Start DE FabLab with `npm run dev` and open <http://localhost:3000/prototypes>. Prototypes is on by default in development. Without a credential, every page still opens and the seeded examples still show, but Generate, refinements, reviews, and lesson proposals are unavailable.

`npm run config` prints the Prototypes settings in effect. The README lists each setting and its environment variable.

## What is seeded and what is live

Every new workspace starts as a copy of one rehearsed workspace, `src/lib/prototypes/seed/seed.json`, which the real pipeline produced through AI Gateway. Viewing it calls no model. It holds:

- the five fictional personas, the default page shell for Meridian Corporate Banking, and three benchmark intents
- Cut-off countdown queue, a payments page for Maya Lindqvist with three versions: each was rated, the notes became lessons, and version 3 adds the over-USD-1m confirm step
- a fork of its version 3, and a pairwise review of its versions 1 and 3
- Shortfall-first summary, a liquidity page for Daniel Okafor, refined once, and Owner-first blocker table, an onboarding component for Wei Chen
- three active lessons from the feedback, three proposed from recurring check failures, six generations of progress, and one lesson check

Live, during a demo: generating, refining, the persona-fit review, proposing lessons from new feedback, the lesson check, accepting templates, share links, downloads, and Sandbox.

Accessibility audits run in the browser, so a seeded version's audit runs the first time someone opens its preview, with no model call.

## Presenter script

About 15 minutes. Use a fresh browser profile or a private window, so the workspace is new.

1. **Frame it (1 minute).** All Prototypes lists the seeded examples. Point at the AI-generated notice: everything here is fictional.
2. **Personas (1 minute).** Personas shows the five examples. Open Maya Lindqvist: her goals and constraints are what every review scores against.
3. **Start a live generation (1 minute).** New prototype: search for Maya, enter "Review and release today's urgent payments before cut-off", keep Page and 3 variants, and select Generate. Three variants take about six minutes with their reviews, so leave them running.
4. **A prototype's history (3 minutes).** Open Cut-off countdown queue.
   - The thread shows each message and the version it made.
   - Preview: switch to Dark, then High density, then Mobile, where the navigation moves behind the menu button.
   - Checks: the four gates, any repairs with the first-pass result, the accessibility audit, and the persona-fit review with its intent-specific checks.
   - Code: the generated page, its sample data, and the shell's source.
   - Provenance: the Salt guidance consulted, the lessons applied, and Salt 1.73.0 for both rendering and guidance.
5. **Lessons (2 minutes).** Lessons shows what the ratings and reasons taught, each citing its feedback, and three proposals drawn from check failures that kept recurring, ready to accept live. Progress compares the earliest and latest generations with measured values, and the lesson check shows how benchmark intents fared with and without lessons.
6. **Compare (1 minute).** On Cut-off countdown queue, compare v1 with v3: both previews under one set of controls, the higher scores marked, the code changes, and the pairwise review.
7. **Back to the live generation (2 minutes).** The variants page shows three directions on the same sample data. Keep one with a reason and discard another with a reason. Each reason can become a lesson.
8. **Accept as a template (2 minutes).** On Cut-off countdown queue v3, select Accept as template, give it a title, a description, the Payments brand, and tags, and continue. If Salt Patterns selects any Standard Release, the confirmation assesses the version's exported project and evaluates it against them, which takes a few seconds with the worker running; any Gap or Indeterminate Finding blocks acceptance and is listed with its Release and Control. With none selected, it says Not evaluated and links to the Salt starters. Confirm. Salt Patterns now shows 17 templates. Filter by Origin, From Prototypes, and open it: Community, "Accepted by Anonymous visitor (unverified)", template v1, and its version history. Use template starts a new prototype from it.
9. **Take it out (2 minutes).** Share or download: create a share link and open it in another private window; it shows the version and its checks and nothing else. Download v3 is a Vite project that runs with `npm install` and `npm run dev`. Open v3 in Vercel Sandbox gives a public address in under a minute that stops after 30 minutes.

If live generation is slow or the model service fails, stay on the seeded prototypes: every beat except 3 and 7 uses them.

## Reset

- **Prototypes:** All Prototypes, More actions, Reset Prototypes. It deletes the workspace's prototypes, versions, feedback, lessons, personas, page shell, and share links, and restores the seeded examples. Templates it accepted stay in the gallery, and today's generation count stays as it is.
- **The template demo:** reset it from Add application's More actions menu. Accepted templates survive that reset too.
- **Everything, locally:** stop `npm run dev`, delete `storage/prototypes-pglite`, and run `npm run prototypes:migrate`.

Each workspace can generate 500 variants a day (`FABRICATE_PROTOTYPES_DAILY_LIMIT` changes it); refinements and automatic repairs count toward it, and it resets at midnight UTC. Workspaces idle for 30 days are deleted, keeping the templates they accepted.

## Live generation timings

From the run that captured the current seed (`npx tsx scripts/capture-prototype-seeds.ts`), through AI Gateway with Claude Opus 5.5 writing, Claude Sonnet 5.5 planning and learning, and Gemini 3.1 Pro reviewing:

- A variant, from planning to its review, took 198 seconds at the median and 308 at the longest, across 16 variants.
- Per stage, at the median and the longest: planning 47 and 52 seconds, writing 76 and 142, repairing 48 and 127, and reviewing 34 and 41. Ten of the 16 needed at least one repair.
- The first beat's three page variants finished in about four minutes, because variants run at the same time. A refinement took about two minutes, and the six-variant lesson check about six.
- The whole rehearsal, 12 generations, took 21 minutes.

So start the live generation early in the demo, and show seeded prototypes while it runs. The seeded lesson check reads "won 0, lost 1, undecided 2": present it as a measurement on three benchmark intents, not as proof either way.

## Capture the seed again

After a change to the pipeline, the Salt kit, or Salt itself, capture a new seed:

```sh
npx tsx scripts/capture-prototype-seeds.ts
```

It runs the rehearsal in `src/lib/prototypes/seed/rehearsal.ts` through AI Gateway on an in-memory store, so it never touches `storage/prototypes-pglite` or a running server, then writes `seed.json` and prints its timings. It generates about 20 variants. Commit the new `seed.json`. When only the runtime build changes, new workspaces recompile the seeded code without a new capture.

## Hosting on Vercel

The Vercel project is `hippobyte/fabricate`. It deploys only Prototypes, in the hosted profile, with Neon for storage. Builds can't reach the internal registry that serves `@repo-facts`, so the project has no Git connection: a machine that can reach the registry builds it and uploads the result.

The project already has:

- Neon (`fabricate-prototypes`), connected to production and preview only, so `vercel env pull` never puts `DATABASE_URL` in `.env.local`
- `FABRICATE_PROFILE=hosted`, `FABRICATE_PROTOTYPES=true`, and `FABRICATE_DEMO=false` on production
- Deployment Protection with Vercel Authentication on all deployments
- an AI Gateway budget on the project

To deploy:

1. Pull production's settings, which go to `.vercel/`, not `.env.local`:

   ```sh
   vercel pull --yes --environment=production
   ```

2. Apply any new migrations to Neon:

   ```sh
   set -a; . ./.vercel/.env.production.local; set +a
   FABRICATE_PROTOTYPES_DATABASE="$DATABASE_URL_UNPOOLED" npm run prototypes:migrate
   ```

3. Build from a clean copy, never from a working directory. Next traces the proxy and the instrumentation hook over the whole project directory, so a build in a working directory would upload `storage/` (local databases), `tmp/`, and test output. A fresh clone is clean; from a working directory, copy what the build needs:

   ```sh
   D=/tmp/fabricate-deploy && rm -rf "$D" && mkdir -p "$D/.vercel"
   rsync -a --exclude node_modules --exclude storage --exclude tmp --exclude verification --exclude test --exclude e2e \
     --exclude docs --exclude dist --exclude test-results --exclude playwright-report --exclude '.next*' --exclude .git \
     --exclude .vercel --exclude .env.local --exclude public/prototype-runtime ./ "$D/"
   rm "$D"/playwright*.config.ts "$D"/vitest.config.ts
   cp .vercel/project.json .vercel/.env.production.local "$D/.vercel/"
   cp -cR node_modules "$D/node_modules"   # an APFS clone; use cp -R elsewhere
   ```

4. Build, fix up, and upload, with `REPO_FACTS_NPM_REGISTRY` set so dependencies resolve:

   ```sh
   cd "$D"
   vercel build --prod
   node scripts/vercel-prebuilt-fixup.mjs
   vercel deploy --prebuilt --prod
   ```

   The fixup adds `.next/package.json` to the proxy's function, which Vercel's builder leaves out; without it every request fails with `ERR_REQUIRE_ESM`, because the package is `"type": "module"`.

5. Smoke-test the deployment: sign in through Vercel Authentication, open `/prototypes`, generate one variant, and keep it.

To let someone without a Vercel account in, create a shareable link under the project's Deployment Protection settings. To roll back, promote the previous deployment in the dashboard, or set `FABRICATE_PROTOTYPES=false`, after which every Prototypes surface answers not found.

On Vercel, Prototypes has no Salt Patterns gallery, since the template demo isn't hosted yet, so Accept as template isn't offered there.

**Known issue: previews don't render behind Deployment Protection.** The preview frame is sandboxed to an opaque origin, so its requests for the Salt runtime under `/prototype-runtime/` carry no sign-in cookie, and Vercel Authentication redirects them. Generating, the checks, reviews, and keeping work; the frames stay blank. The planned fix is to serve the runtime, which holds only public packages, from a separate public static project.

## Generating the hero templates

The four hero templates' microfrontends and the Access and Markets shells are written by the Prototypes pipeline itself, once, and committed:

```sh
npm run heroes:generate                          # every hero and both shells, with AI Gateway
npm run heroes:generate -- --hero client-onboarding --skip-shells   # one hero again, keeping the rest of the committed output
npm run heroes:generate -- --index-only          # rebuild pages, index, sources, and manifest from the committed files, with no model
npm run heroes:generate -- --hero payments-workspace --mock --out tmp/heroes   # one hero, mock models, to try it offline
```

It runs in-process on an in-memory Prototypes store, so it never touches `storage/prototypes-pglite` or a running dev server. A full run takes about 20 minutes. For each hero it:
1. Lifts one shared `data.ts` from the hand-written members in `src/demo/runtime/members/`: their interfaces, types, and capitalized record arrays, with no model.
2. Ports each microfrontend's stable version, its latest that is neither a prerelease nor planted, from its hand-written source to Salt. The port keeps every visible text, accessible name, record, bus topic, and `data-demo-anchor`, so the runtime, its toolbar, and their tests work as before.
3. Ports the other versions as refinements of the stable one. A planted version is asked for exactly the catalog's `planted` rules, and those are its only gate exemptions; the Salt-only gate's result records each one.
4. Composes the main route into one `page.tsx` (`src/lib/prototypes/heroes/flatten.ts`), which Use template, variant 0, and the hero's Standards use. The run stops if the page fails the gates.

A version whose gates still fail after repair is generated once more before the run stops, and the error names the failing issues.

It writes to `src/demo/runtime/generated/`:
- `<hero>/data.ts`, `<hero>/<member>/<version>.tsx`, and `<hero>/page.tsx`
- `shells/<kind>.tsx` and `shells/data.ts`
- `index.ts`, which the runtime's registry imports, and `sources.ts`, which the Code tab and Use template read
- `manifest.json`, with each version's gates, exemptions, and provenance

A generated version takes the place of the hand-written one it names, and the others stay until they're generated. Review the output, run `npm test` (`test/lint/generated-heroes.test.ts` checks that every file uses only Salt's tokens outside its planted rules, and `test/prototypes/hero-template.test.ts` that every hero's page meets both Salt starters), then the runtime's browser tests (`e2e/runtime.spec.ts`, `e2e/microfrontends.spec.ts`, the toolbar specs, and the storyline), then commit it. Generated members render under Salt's provider, which applies only inside the portal's root.

**Hand edits.** Fix a generated file by hand when the model won't produce what the storyline needs. The model names icon buttons, for example, so the planted button-name defect was restored by hand. Add a sentence to that version's (or shell's) `provenance.edits` in `manifest.json` saying what changed and why, then run `--index-only` so `sources.ts` and the pages match. A later run of that hero overwrites its edits, so check its manifest first.

## The portal runtime interface

Hero templates' microfrontends and shells import `@deweb/portal` for what they share with the running portal. It has the same API in the portal and in a prototype's preview frame:

| Export | In the running portal | In the preview frame |
| --- | --- | --- |
| `useBus(topic, member, handler)` | Subscribes on the application's event bus; the toolbar records every message | Subscribes on the page's own bus, shared by its regions |
| `usePublish(member)` | Publishes on the application's bus as `member` | Publishes on the page's own bus |
| `useProfile()` | The active session profile: `name`, `persona`, and `region` | The version's first persona: its name, its role as `persona`, and no region |
| `useRoute()` | The current route and every route of the application, each with its `href` | The page itself as the only route; its `href` is `#` |
| `routeHref(route)` | The route's address, kept embedded in Preview mode | `#` |
| `useNavigate()` | Opens a route without reloading the page | Does nothing |
| `useApplication()` | The application's `name`, its `portal`, and its `environment` | The page's title as `name`, and no portal or environment |
| `planted.blockMainThread(ms)` | Busy-waits for `ms` milliseconds, the planted slow interaction | The same |

In the portal, a path alias in `tsconfig.json` resolves it to `src/demo/runtime/portal/`. In the frame, the prototype runtime's import map resolves it to `deweb-portal.js`, which `scripts/build-prototype-runtime.mjs` builds from `src/prototypes/runtime/portal.ts`. Only versions that start from a hero template may import it; the Salt-only gate refuses it everywhere else.

## Upgrading Salt

Prototypes renders with one Salt release, and its generator and checks use a registry built from that release's own source. The two must match: a test fails when the committed registry and the installed Salt packages differ.

To move to a new Salt release:

1. Bump every `@salt-ds/*` package in `package.json` to the release's matching set, with exact versions, and run `npm install`.
2. Rebuild the registry. The script reads the installed `@salt-ds/core` version, shallow-clones salt-ds at the matching `@salt-ds/core@<version>` tag into `tmp/`, and runs `@salt-ds/mcp`'s `buildRegistry` over it:

   ```sh
   node scripts/build-salt-registry.mjs
   ```

3. Run `npm test`. `test/prototypes/salt/registry.test.ts` checks that the registry lists the installed version of every Salt package, and `test/prototypes/salt/adapter.test.ts` checks the `@salt-ds/mcp` tools still answer as the generator expects.
4. Commit `package.json`, `package-lock.json`, and `src/lib/prototypes/salt/registry/` together.

After the upgrade, the first visit to Salt Patterns re-checks every accepted template against the new release without calling a model, and marks each Unchanged, Fixed, Regressed, or Broken. A Broken template stays listed with its failures, and Use template is unavailable until a fixed version is accepted.

A template that was evaluated when it was accepted is also assessed again. Its export, with `package.json` now pinning the new Salt, is evaluated against the same Releases its acceptance used, with the worker running. A Control that stopped meeting marks the template Regressed, and its page names the Control, unless a gate makes it Broken.

When every re-check for the new build has finished, Salt Patterns offers the upgrade report as Markdown or JSON, also at `/api/prototypes/templates/upgrade-report?runtime=<hash>`. It lists each live template's latest version with every gate and Control, in `salt-fleet-crater`'s terms: unchanged, regressed, fixed, or broken. Its header explains how those terms map to the gallery's badges, and states what the checks don't cover.

If `buildRegistry` fails on a later tag, the script stops with an error and the committed registry keeps serving the current release. Hold the upgrade until the registry builds.

The registry bundled inside `@salt-ds/mcp` describes an older release, so DE FabLab never loads it. To move `@salt-ds/mcp` itself to a newer snapshot, pin the exact snapshot version, rebuild the registry, and run the adapter contract test.
